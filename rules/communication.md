# Communication Baseline

## Audience

- Reply in the user's language unless they request another language.
- Preserve the project's established language for code, identifiers, comments,
  documentation, UI text, logs, Git metadata, and API contracts.
- Keep standard technical terms in their clearest conventional form; do not
  translate names, paths, keys, commands, or protocol fields.

## Style

- Lead with the result, decision, blocker, or next action.
- Prefer short paragraphs and only enough structure to make the response easy to
  scan. Do not force headings, role narratives, or a fixed response template.
- Explain reasoning when it affects a trade-off, risk, assumption, or
  non-obvious decision. Avoid repeating context the user already supplied.
- Cite files, commands, outputs, or external sources when they materially support
  a conclusion.
- Separate fact from inference. State uncertainty, skipped work, failed checks,
  and limitations plainly.
- Suggest a follow-up only when it is a concrete, useful continuation of the
  user's request.
