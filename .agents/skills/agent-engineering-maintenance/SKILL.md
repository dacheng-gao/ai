# Agent 工程环境与规则维护

让 agent 能自行获取事实、探索方案、实施和验证，把人的注意力留给环境中无法推导的目标、业务选择与重大后果。改进对象是支持这条反馈循环的工程环境和规则，不是提示词长度或代码产量。

## 从实际阻碍进入

先从用户请求、现有对话和适用规则确定对象与权限：

- **检查、评审或建议**：读取相关资料，执行适当的非破坏性检查，给出发现与最小修复建议；不修改项目或个人配置。
- **维护、修复或落实**：完成已授权范围内的修改和验证，不把已有授权重新变成审批问题。
- **只处理某次任务**：解决直接阻碍即可，不借机开展全仓治理。新增一个 skill 也不意味着获准将其建议应用到来源项目。

范围不明确时，从当前仓库及用户指出的问题开始。个人配置、其他仓库和外部系统不因工具可访问而自动纳入修改范围。没有实际症状的就绪检查，可围绕一条典型的本地“定位实现 → 修改 → 验证”路径抽样；不必真的改业务代码。

新建协作环境或用户要求“从零设计再对比”时，先按下表推导各层最小职责，再对照现有入口和实际任务找差异。这个设计是比较基准，不要求清空重写或补齐每类文件。保留已经有效的安排及明确延期决定，只落实有依据且已授权的差异；普通局部维护无需重新设计整套体系。

## 建立最小证据链

从适用的 `AGENTS.md`、项目入口、相关构建/测试配置及用户给出的失败记录入手；只沿与问题有关的链接阅读。按需使用 [检查与维护参考](references/checks.md) 中对应的主题，不默认执行所有检查。

核实 agent 是否能回答：事实去哪里找，怎样获得可信反馈，哪些操作被实际限制，什么结果算解决了原始问题。缺少某类文件不自动构成缺陷；已有工具或约定能完成同一目的就复用。

每个实质发现保留简短的证据链：**位置或命令与结果 → 实际影响 → 最小行动 → 验证方式**。区分观察、推断和未验证事项；优先处理阻塞执行、误导决策或反复消耗人类注意力的问题。不能仅凭存在测试脚本就断言测试可运行，也不能把权限或依赖缺失导致的未执行写成通过。

检查命令执行前，读清相关脚本的副作用和环境目标。检查模式不运行自动修复、安装、迁移、部署或外部写入；必要的本地测试产物应限定在临时或项目约定的生成目录。无法安全验证时说明具体缺口，不靠扩大权限获得“全绿”。不读取或输出与问题无关的凭据值。

## 把信息放到合适的位置

| 信息或问题 | 优先落点 | 维护判断 |
| --- | --- | --- |
| 跨项目稳定的个人协作偏好 | 用户全局规则 | 只在授权范围内维护；不放项目事实、业务契约或一次性选择 |
| 项目或目录的稳定协作约束 | 根规则、局部规则及既有专门规范 | 保留作用范围、必要例外和真实授权边界；共享项目不能依赖维护者的私有全局配置 |
| 当前能力、配置、运行和检查入口 | 既有 README 或操作文档 | 命令集中维护，规则链接到入口；缺少反馈时修实际路径，不只增加“必须验证” |
| 目标行为、验收、技术决定和交付状态 | 既有规格、设计、任务记录 | 规格回答应当怎样；设计区分当前实现、目标方案与待决事项；任务记录完成状态和证据，彼此引用 |
| 可确定执行的约束 | 现有 formatter、静态检查、测试、数据库约束或权限配置 | 选择能覆盖实际问题的最小机制，先确认变更影响 |
| 可复用的环境诊断与维护方法 | 维护 skill 及按需参考 | 按症状进入；不把日常开发变成每次必做的治理流程 |
| 本次目标、临时假设与例外 | 当前对话或已有任务记录 | 不把一次性选择升级为永久规则 |

规则冲突需区分指令优先级、适用目录、明确例外与事实陈旧。源码和运行结果说明当前行为，不自动决定业务上应该怎样；讨论文档也不自动成为执行指令。只能按当前运行环境的指令层级解释规则，不能自创优先级。

删除或合并规则前确认其原意与作用范围仍由保留的规则或机制覆盖；迁移内容时同步原入口和受影响链接。不要仅因个人全局规则已有同义条款就删除团队共同约束。已有机器检查不代表解释其业务原因的文字都应删除。来源无法裁定、且会改变业务契约或授权的冲突，应提出一个聚焦问题，继续不依赖该答案的工作。

## 实施最小维护

获准维护后，优先修复失效入口、过时命令、重复或冲突规则，以及已证实缺失的反馈。沿用项目工具，不为“agent 友好”新建框架、完整知识库、评分系统或长篇任务模板。

让 agent 自行承担检索、整理、执行与收集证据。只有实际重复且稳定的步骤才值得脚本化；只有明确可检验的约束才转为自动检查。提示词不能替代权限隔离、审批或回滚；不能为减少打断而放宽安全、数据和发布边界。已授权操作按现有权限执行；尚未授权的高影响动作先准备可审查的具体改动，再按适用规则处理授权。

提问前先调查可查证事实。可逆且符合项目惯例的选择可以说明假设后推进；影响业务语义、外部契约或不可逆后果的缺失信息，给出建议和差异后聚焦提问。不要要求用户填写环境能够补齐的任务表单。

如果修复没有产生新证据，停止堆补丁或重复同类检查，回到最小复现和原假设。新增规则应有当前问题依据；探索性设想先作为建议，不强制推广。

## 验证是否真正减负

针对修改重走受影响的入口或命令：链接能否定位权威资料，验证是否实际执行，冲突是否消除，操作边界是否仍成立。机器检查需要覆盖已知问题，并有来自既有契约、业务实例或独立预期值的依据；不以放宽断言、跳过失败或只测试本次实现来制造成功。

再检查协作结果：agent 能否自行回答原来反复询问的事实，工程师能否从简短结果理解关键行为与失败边界，新流程是否反而增加阅读、审批或维护负担。局部修复不需要全套评估；审查或交接困难时，优先缩小可验证改动、说明关键契约，不要求人理解全部生成细节。

有真实前后记录时，可比较必要人工问答、返工或验证障碍，并观察后续普通任务能否在无需额外维护流程的情况下利用修复后的入口与反馈；没有记录时，只说明预期收益，不声称已证明效率提升。结构验证通过也不等于模型会稳定遵守该 skill。

完成时简要报告：关键发现及证据、已改内容或待实施建议、实际验证、影响使用的未决项。抽样检查明确覆盖范围；没有实质问题就直接说明，不制造改进任务。除用户要求或既有流程需要外，不另建报告文件。完成当前范围后停止。

## 技能自身维护

修改本 skill 的选择或行为边界时，使用 [回归场景](references/evaluation.md) 做针对性检查；日常项目维护无需加载这些场景。
