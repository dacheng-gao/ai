# 用质量场景驱动架构决定

下面的工作方法将 *Software Architecture in Practice* 的质量属性视角、C4 的表达方法、ADR 的决策记录连接起来。是可裁剪的工程综合，不是完整 ATAM 评估程序。

## 质量属性场景与机制

对影响当前设计的质量要求写出：谁/什么产生刺激、运行环境、受影响的系统部分、应做出的响应及衡量方式。将“易修改”落实为哪种已预见变更、哪些调用者需要保持稳定；将“可靠”落实为哪种故障下哪些任务仍须完成。

每个重要场景要能连接到设计机制及其代价。例如缓存可能改善读取延迟，但引入新鲜度、失效与运维成本；异步处理可能隔离慢依赖，但需要明确何时算成功、如何查询结果和处理失败。没有场景支持，不因技术可用就采用。

遇到质量目标冲突，说明哪个已确认要求优先、哪项需要业务取舍。不能自行把“提交时不得超额”改成“后台稍后修复”，也不能把未测量的架构草图称为性能达标。

## 视图应回答的疑问

- 上下文：系统服务谁、依赖什么、哪些责任在系统之外？
- 容器：哪些可运行应用/服务与数据存储承担责任，如何通信？
- 组件：某个容器内部的职责划分只有在当前问题需要时展开。
- 动态/部署：时序、失败、拓扑会改变判断时分别表达，不将逻辑模块冒充实际部署。

标清箭头含义、调用方向、协议及重要信任边界。图与真实接口、部署约束矛盾时修正模型；无需画代码级图来重复源码。

## 权衡与决策记录

使用真实约束比较能够实施的方案，必要时包含维持现状、先改索引或模块再考虑分布式拆分等渐进方案。结论说明选择依据、接受的代价、剩余假设和重审信号。无真实分歧时直接记录理由，不凑备选。

需要保留长期理由时，用已有 ADR 形式记录背景、状态、决定与后果。提案不写成已批准；被替代的决定保留历史联系。不要为所有函数和局部编码选择建立 ADR，也不强制作者原文中的目录、编号或篇幅约定。

## 技术试验

将未知写成可证伪问题：目标供应商在指定条件下是否支持某操作？候选事务协议能否拒绝某个竞争历史？指定规模与分布下哪段路径超出已有目标？

选择最小原型与代表性输入，预先确定观察结果、失败判据和资源边界。性能记录硬件、版本、数据分布、负载方式、错误率和时间口径；并发试验展示交错与提交后事实。结果不满足目标时更新方案，不静默换指标。

试验结束交付结论及局限，丢弃或明确标记临时代码。没有真实负载或目标环境时，只能证明试验范围内的可行性。

## 演进走查

沿关键业务流检查新旧调用者、数据写入者和部署顺序。按需要设计扩展 → 兼容过渡/回填 → 切换 → 收缩，验证约束与观测点。停机窗口允许时简单停机迁移也可能更合适，不默认引入双写。

问能否在失败处恢复到一致状态；若数据已不可逆转换，给出向前修复、备份恢复等真实可行选项及代价，而非笼统“回滚即可”。执行阶段交给当前发布流程，设计本身不授权操作生产环境。
