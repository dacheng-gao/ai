# 稳定性、数据流与分布式演进

仅在涉及跨进程调用、外部依赖容错、分布式数据一致性、异步集成或大粒度系统拆迁时读取。综合 Michael T. Nygard《Release It!》（第 2 版）、Martin Kleppmann《Designing Data-Intensive Applications》、Gregor Hohpe / Bobby Woolf《Enterprise Integration Patterns》、Neal Ford 等《Software Architecture: The Hard Parts》与 Sam Newman《Monolith to Microservices》的公开方法；核查范围见 [来源映射](../../software-delivery/references/sources.md)。

## 稳定性反模式与防雪崩模式（Release It!）

分布式故障很少来自单点直接崩溃，更常来自慢依赖拖垮上游资源池而引发的级联故障。设计或评审任何跨进程边界时，对照以下反模式与保护机制：

| 常见反模式 | 典型失控机制 | 对应稳定模式与设计要求 |
| --- | --- | --- |
| **集成点无超时或过长超时** | 下游挂起占满调用方线程/连接，最终拖垮整个上游 | 为连接、读取和整次请求设明确**超时预算**；不把默认无限等待带入生产 |
| **盲目重试导致重试风暴** | 下游过载变慢，上游齐刷刷重试使流量成倍放大 | 仅对幂等操作做**有界重试 + 指数退避 + 抖动（Jitter）**，配重试预算或**断路器（Circuit Breaker）** |
| **共享资源池引发级联故障** | 非核心依赖变慢耗尽主连接池/线程池，连累核心业务 | **舱壁隔离（Bulkhead）**：按关键度或依赖隔离线程池、连接池和队列 |
| **无界结果集 / 无界队列** | 一次大查询或下游积压撑爆内存与 GC | 强制分页/结果上限、有界队列、**背压（Backpressure）**与必要时的**限流/降载（Load Shedding）** |
| **长期运行状态无限增长** | 日志、临时表、未清理缓存或死信不断堆积直到耗尽磁盘/性能 | **稳态设计（Steady State）**：明确数据保留、清理、轮转与归档策略 |
| **等待失败再拒绝** | 明知下游不可用或资源耗尽仍排队消耗预算 | **快速失败（Fail Fast）**：尽早拒绝并返回可降级或可区分的错误 |

不要盲目堆砌所有组件（例如给低频内部调用硬上复杂服务网格）；先守住**超时、有界结果、幂等与隔离**四项底线。

## 数据流、一致性与异步集成（DDIA & EIP）

1. **区分记录系统（System of Record）与派生数据（Derived Data）**：明确哪一份数据是业务事实的权威来源；缓存、搜索索引、物化视图、分析宽表均为派生数据，须说明刷新延迟、失效口径以及**从权威源重建/核对**的办法。
2. **按业务需求精确命名一致性，不笼统说“最终一致”**：
   - 写后立即回查同一对象：检查是否需要**读己之写（Read-your-writes）**（避免写主库后马上从滞后副本读不到）。
   - 连续读取不倒退：检查是否需要**单调读（Monotonic reads）**。
   - 强约束（余额、库存、唯一名额）：明确需要线性一致/单权威事务协议，不能用异步事件代替提交时裁决。
3. **跨边界可靠交付（事务外发 + 幂等接收）**：
   - 严禁“提交本地库后再裸发消息/调外部接口”却不处理中间崩溃；需要可靠通知时采用**事务外发（Transactional Outbox）**或等价的持久化意图记录。
   - 网络交付默认至少一次（At-least-once）：消费端必须实现**幂等接收（Idempotent Receiver）**，明确去重键作用域与保留期，并规划乱序到达的处理语义。
   - 异步通道须明确**关联标识（Correlation ID）**、**死信通道（Dead-Letter Channel）**与人工/自动重放条件，避免毒丸消息无限重试阻塞队列。

## 拆解权衡与渐进拆迁（The Hard Parts & Monolith to Microservices）

考虑拆分服务或迁移旧系统时，同时列出**拆解驱动力**（独立部署、故障隔离、独立伸缩、团队自治）与**聚合驱动力**（强事务一致性、高频细粒度共享数据、共享业务流程耦合、运维与观测开销）。数据所有权无法理清前，不要先拆服务进程。

- **禁止多服务共享同一张业务写表**：若两个服务必须共同维护同一组强不变量，往往说明它们应留在同一边界内，而不是拆成共享数据库的分布式单体。
- **跨服务工作流（Saga）的真实代价**：一旦放弃本地 ACID 事务，必须显式设计补偿动作、中间可见状态与语义锁；评估业务能否接受“先扣款后补偿”再决定是否拆分。
- **渐进拆迁模式**（优先于大爆炸重写）：
  - **绞杀者模式（Strangler Fig）**：在入口路由或网关层拦截特定路径，按业务切片逐步切流到新实现，保留回退路径。
  - **抽象分支（Branch by Abstraction）**：在代码内部先建立稳定抽象层，逐步用新实现替换旧实现，全程保持主干可发布。
  - **并行运行比对（Parallel Run / Dark Launch）**：在不影响主结果的前提下用真实流量影子对比新旧输出，验证一致后再切换写权威。
