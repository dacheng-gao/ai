# 以复杂度为首要考量的软件设计

当任务涉及模块边界、公开 API、服务拆分、数据所有权或非简单重构时，应用这些原则。目标是降低整个系统中理解和修改代码的成本，而不是追求更多抽象、层次或组件。

## 从复杂度入手

- 识别设计必须支持的变更、调用方目前需要了解的细节，以及规则或决策被重复定义的位置。
- 将依赖、信息泄露、特殊情况和不直观的控制流视为复杂度信号。
- 优先采用能够隐藏相关复杂度的最小设计，并为依据证据演进保留清晰路径。

## 塑造边界

- 优先采用深模块：通过小而具有明确语义的接口，隐藏大量实现知识。拒绝仅转发调用或为技术细节改名的浅层包装。
- 围绕业务能力或稳定的变更原因组织代码；在有益时，将 API、应用、领域和基础设施关注点保留在该边界内。
- 为每项业务规则、数据解释和外部系统策略保留唯一的权威归属方。防止数据库模式、供应商协议和传输细节泄露给调用方。
- 让接口明确且具有清晰语义。调用方应表达意图（例如 `findPendingOrders`），而不是自行重建存储机制。
- 不要仅因模块规模大就拆分模块，也不要仅因存在共享代码就合并模块。应以耦合程度、变更影响和信息所有权为依据。

## 审慎选择

- 对于重要决策，比较至少两种合理的设计，并说明在复杂度、失败行为、可测试性、运维和未来变更成本方面的权衡。
- 区分战略性设计工作与战术性补丁。对于会反复出现、被广泛依赖或难以撤销的决策，应投入设计精力；对于低风险的局部选择，保持简单。
- 不要推测所有可能的未来。仅围绕已观察到或受到严格约束的变化进行泛化，并记录哪些假设会支持重新审视边界。
- 将重复视为需要调查的信号，而不是自动重构的目标。当概念可能分化时，重复可能比过早引入共享抽象更安全。

## 评审实现质量

检查所提设计是否：

1. 减少调用方和未来维护者需要掌握的知识。
2. 将可能发生的变更集中在局部，而不是分散到各个层次或服务中。
3. 让常见路径清晰直观，并将异常情况控制在局部。
4. 保持明确的依赖方向，防止为了方便而跨越边界访问。
5. 能够在负责该行为的边界上进行测试，而无需重建整个系统。
6. 在改变公开契约或数据边界时，包含明确的迁移或回滚路径。

评审或提出架构方案时，先说明结论，再给出证据、假设、被否决的替代方案，以及哪些信号会支持改变决策。按实际需要适度应用这些原则；本技能不要求采用特定的架构风格、语言、框架或微服务。
