# 缺陷诊断协议

以 David Agans《Debugging: The 9 Indispensable Rules》为骨架，结合 Andreas Zeller《Why Programs Fail》的**感染链（Infection Chain）**与**最小化复现（Delta Debugging）**思路，整理为 agent 科学调试步骤（观察 → 假设 → 可区分的实验 → 结论）。目标是用最少的观察找到真实原因，而不是猜测式修改。

## 区分失效、感染与缺陷（Zeller 感染链）

程序出错遵循一条因果链：**缺陷（Defect，代码或配置里的错误）→ 状态感染（Infection，执行到某处后内部状态首次偏离预期）→ 失效（Failure，外部观测到的报错或错误结果）**。调试必须从观测到的失效逆向追到**最早出现状态感染的那一步**；只在最终失效点加判断掩盖症状，通常会留下同源缺陷。

## 步骤

1. **写清症状**：期望行为（来源：规格、契约或用户描述）、实际行为、触发条件、首次出现的版本或时间。没有期望行为的依据时，先确认“这是不是缺陷”。
2. **让它稳定且最小地复现**：找到最小、可重复的复现（测试、脚本、请求或操作步骤）。面对庞大输入或大段改动时，按 Delta Debugging 思路**系统性折半缩减输入或配置**，直到删掉任何部分都不再复现。间歇性问题记录出现频率和相关条件（并发、时间、数据、环境），并优先检查跨调用残留的共享状态（全局变量、可变默认参数、缓存、单例、连接池），在同一进程内连续调用来复现，不要因为一次没复现就宣布修好。
3. **先看再想**：读真实日志、错误栈、数据和执行路径，而不是凭代码印象推理。检查“插头”类前提：运行的是不是改过的代码、配置和环境变量是否正确、依赖版本、缓存、数据是否是以为的那份。
4. **提出可区分的假设**：列出 2–3 个候选原因（输入、规则、持久化、依赖、展示、环境），为每个找一个能区分它们的最便宜观察。复现本身已直接指明原因时跳过此步。
5. **沿感染链二分缩小范围**：在数据流、调用链、提交历史（如 `git bisect`）或输入规模的中点检查状态是否已被感染，每次砍掉一半排查空间，直至锁定首个从“正常状态”变成“感染状态”的位置。
6. **一次只改一个变量**：每次实验只改变一个因素；无效的试探性改动立即撤回，不留在代码里。
7. **记录轨迹**：简要记下做过什么观察、看到什么、排除了什么，避免绕圈；不输出冗长内部推演。
8. **卡住时换视角**：连续两轮没有新信息，回到第 1 步重读症状和前提，或向用户说明已排除项并请求缺失的信息。
9. **证明修好了**：用原始复现验证修复，再检查受影响的相邻行为；能说清“为什么之前出错、为什么现在正确”。说不清原因的改动只能称为“修复候选”。

## 修复范围

- 修根因，不只在症状处加判断；若只能先止血，明确标为临时措施并说明根因位置。
- 为已确认缺陷补一个回归检查，表达正确契约（而不是固化旧输出）。
- 发现同类缺陷存在于其他位置时报告，不在未授权范围内批量修改。

## 无法复现时

报告已尝试的复现条件、已排除的原因、仍可能的候选，以及需要什么额外证据（日志级别、样本数据、环境信息）。不把未经证实的改动称为修复。
