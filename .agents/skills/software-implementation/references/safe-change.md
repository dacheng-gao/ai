# 在已有系统中安全改变行为

Fowler 的重构强调保持可观察行为的小步结构变换；Feathers 的遗留代码方法强调先获得反馈能力，再降低修改风险。以下指导是综合应用，不要求将所有历史代码先改成理想架构。

## 先定位风险，再建立观察

从本次入口追踪到规则、存储与外部副作用。列出修改会影响的调用者与现有契约，查看已有测试能否发现相关错误。先建立能区分目标错误的最小复现，不把所有可想象场景都纳入范围。

如果当前行为缺少规格，特征测试可以记录代表性输入下的现状，用来防止无意改变。它证明的是“之前如此”，不是“业务应当如此”。对于已确认缺陷，目标回归测试表达正确契约；旧错误可单独作为复现证据，不能被快照永久固化。

选择稳定、可解释的断言。时间戳、随机标识或排序若本来无语义，按真实契约控制或忽略；不得随意删掉暴露业务差异的字段。大快照难以审查时拆成关键业务结果。

## 引入必要的依赖接缝

真实网络、时钟、进程或数据库依赖阻碍局部反馈时，寻找最小替换点：已有参数、函数边界、模块入口或系统提供的测试工具。只为当前验证隔离必要依赖，不预先建立万能适配层。

优先选择可逆且保持行为的提取或参数化，先验证外部契约未改变，再实现新行为。替身只证明调用方对已建模响应的处理；供应商协议、SQL、并发和权限仍需要相应集成证据。

## 重构与行为变化分步

1. 在有价值的边界确认原有行为或失败复现。
2. 进行足够让本次变更清楚的结构调整，如提取计算、集中重复规则、隔离外部访问；每步保持可观察行为并检查。
3. 引入目标行为，验证规则、失败和兼容条件。
4. 删除本次引入的临时结构，检查最终差异与必要文档。

这不是必须产生四个提交；按任务需要组织小步。重构不是任意清理代码的同义词，外部接口、查询语义或异常行为改变必须被当作行为变更处理。没有测试时可以利用编译器、静态分析和人工走查降低风险，但须明确剩余不确定性。

## TDD 的适用条件

规则和预期已明确、反馈足够快时，先列关键行为例子，选择一个能推动接口设计的失败测试 → 最小实现使其通过 → 在测试保护下重构。先确认失败原因是目标缺失，不能把导入错误当作有效的红灯。

图形探索、未知外部能力或无明确预期的问题可以先做试验；不要用猜测结果驱动正式实现。TDD 是反馈方法，不自动替代系统设计、集成测试或真实需求验证。

## 缺陷诊断与停止

观察到同样症状可能来自不同层：输入、规则、持久化、依赖或展示。每次检查应区分候选原因；记录简洁的证据与结论，不输出冗长内部推演。修复后用原复现和受影响行为验证，避免只验证新增的内部函数。

已有代码能满足需求就保留；结构改进只覆盖本次所需范围。通过相关检查且差异解释清楚时停止，不把一次缺陷修复扩成全面重写。
