# 测试与业务验收

用有区分力的证据回答“符合哪些约定，还存在哪些风险”。从行为澄清时参与，避免把测试当成开发完的固定阶段。

## 建立判定依据

确认本次是设计测试、执行检查、分析失败还是评审结果；设计测试不自动授权线上操作。读取相关规则、实现、已有用例和运行限制，优先复用已有检查。

每个重要检查须有目标风险、前提/数据、刺激、可观察预期与判定依据。需求不明确时，把未知预期写成问题，不能以实际输出自动充当正确答案。数据与操作是否可用于当前环境也应明确。

## 按问题选择方法

读取 [methods.md](references/methods.md) 中相关部分，不强制所有测试技术：

- 规则歧义或验收争议：实例化需求、例子映射；先达成规则理解，再决定是否自动化。
- 多条件决策或生命周期：决策表、等价类/边界值、状态转换与必要序列。
- 回归或跨组件风险：选择能观察真实失败机制的单元、集成、契约或端到端检查。
- 难以穷举的交互与未知风险：有任务目标、时间边界和记录的探索式测试。
- 权限、并发、性能或数据恢复：在对应边界和环境验证；单线程或内存替身不能证明数据库竞争，低负载样本不能证明容量。

按失败后果、变更范围和不确定性安排检查。测试层次是反馈速度和真实性的取舍，不设固定比例或覆盖率门槛。小改动已有足够证据时直接复用，不为了流程新增测试。

## 执行与诊断

对实际执行记录版本/差异、必要环境、命令或操作、预期与结果。先确认测试失败是否揭示产品缺陷、测试缺陷还是环境故障；不通过删除断言或无限重试制造成功。

业务验收使用有代表性的角色、数据和任务，区分功能符合约定、用户能完成任务、业务指标改善。代理模拟走查只能发现潜在问题，不能冒充业务用户签收或真实可用性研究。

## 收敛

给出覆盖的行为、发现的问题、已执行证据和剩余风险；计划、未运行、通过、失败分别表达。发现缺陷只在授权修复范围内改实现，否则提供复现与建议。

当本次约定范围的关键风险已有相称证据，且必要检查完成时停止；“未发现缺陷”不是“没有缺陷”。方法来源为 Adzic 的案例研究、Hendrickson 的探索式测试及公开例子映射指南，见 [来源映射](../software-delivery/references/sources.md)。
