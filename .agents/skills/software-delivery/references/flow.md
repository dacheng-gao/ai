# 协作、知识与工程师减负

用于跨阶段任务、多方交接或明确要求的流程改进。方法综合持续交付的小批次和反馈原则、DORA 研究与日常工程实践，不要求团队采用新仪式。

## 保持一个目标和少量进行中的工作

沿业务切片完成理解、实现、验证与交付准备。遇到依赖等待时，只推进真正独立且不会造成大量半成品的工作。不要为局部利用率最大化开出许多无法完成的分支。

团队流程评审时查看实际开始到完成的时间、等待位置、返工原因与中断；先处理制约整体交付的瓶颈。不能仅凭某位工程师忙碌程度或代码量推断效率。

## 用最小上下文衔接

让下一步能知道：当前目标和范围、已确认规则及出处、已做决定、尚未确定且有影响的问题、当前产物版本与验证记录、下一步可执行动作。短任务在对话内就足够，长任务复用 issue、测试、ADR 或现有工作记录。

不把所有参考文件塞进每个提示；只加载改变当前决定的资料。文档记录稳定契约和非显然理由，易过期细节尽量链接源码/配置。发生变更时更新权威位置，避免复制契约导致多套答案。

模型可以生成候选、检查反例、检索关联和起草产物；确定性工具负责可执行验证。重复思考同一段材料不构成独立证据，多个模型一致也不等于业务事实成立。

## 让自动化减少工作

对重复且规则明确的构建、检查、格式化或数据处理优先复用工具。脚本仅在可重复执行或正确性收益明显时添加，包含失败可见性；不要以默认成功、忽略错误或无限重试掩盖不确定性。

保留工程师对目标、取舍和授权的控制，减少填表、重复确认和无意义中间材料。澄清问题应能改变当前决定；已在上下文解决的事情不再询问。

## 判断是否真的增值

在同类任务中观察需求返工、缺陷、完成等待、人工纠正、无效文件和重复操作；结合工程师对理解成本、打断和维护负担的反馈。先用项目已有数据与少量实际案例，不建立新的个人监控体系。

比较使用前后时说明任务难度、工具、环境和样本差异；不能把一次模型完成任务归因成 skill 提升百分比。一次只调整有证据的问题，保留有效的短路径，避免将每个失败案例变成所有任务的永久规则。

技能维护的行为检验见 [evaluation.md](evaluation.md)；通过有限评估不能证明真实团队长期效率或幸福感已经提升。
