# 可靠交付小批次变更

依据 Humble/Farley 的持续交付原则和 DORA 能力研究，重点是让软件保持可发布、快速反馈并降低变更风险。持续交付不要求每次提交自动上线。

## 制品与流水线

检查项目是否能从明确版本构建出可追踪制品，配置与迁移是否版本化，必要检查是否对将要发布的同一制品成立。尽量跨环境提升同一制品，避免在生产临时重新构建而失去验证对应关系。

把快速编译/静态检查/单元反馈放在前面，更慢的集成和环境验证按实际风险配置。失败时处理质量或环境原因，不将失败忽略后标成可发布。密钥使用项目安全机制注入，不写入制品、示例或日志。

小批次、短反馈和频繁集成减少累积风险；具体分支与审批遵守项目要求，不能从持续交付原则推导出绕过审查。只有重复劳动与收益明确时自动化，不为一次发布重建整个平台。

## 将数据变更纳入发布

明确应用与 schema 的新旧兼容关系、数据量、锁与事务行为、回填进度、唯一/非空约束验证和消费者切换。数据库版本不明时先核实，不能给出伪通用的在线 DDL。

需要不停机过渡时可按扩展、兼容读写、可恢复回填、校验、切换、收缩推进；每步有可观察完成条件。回填失败要能判断哪些记录已处理，不能靠重跑不可幂等脚本修复。允许停机且风险更低时采用简单停机方案。

不要在旧版本仍依赖字段时删除字段；不要把旧代码部署成功当成数据恢复。备份是否可恢复、恢复点意味着多少数据损失，应有证据或明确待验证。

停止写旧字段之前，检查新版本的实际 INSERT/UPDATE 是否仍能满足旧 schema：旧列的 NOT NULL、默认值、检查约束、生成规则、触发器，以及旧读者/后台写者的依赖。必要时先做兼容约束调整再切换写入；验证新旧版本各自的新增与修改路径，而不只校验已有行。默认值不能用来伪造仍被消费者使用的业务事实。

恢复要求与每步风险相称。应用回退足以撤销的兼容部署、可暂停且以原字段重建的回填，不自动要求完成全库恢复演练才能准备或推进；不可逆删除或数据转换需要与损失相称的恢复证据。未验证的恢复能力明确标出，不能因此给所有步骤加统一审批门槛，也不能跳过真正必要的恢复验证。

## 选择发布控制

单一低风险应用可能只需要标准部署与健康检查。风险和基础设施支持时，使用分批、灰度或蓝绿；说明真实流量/状态如何切换，哪个信号决定继续或终止。

功能开关可分离部署与用户曝光，但有组合测试与清理成本。为当前开关说明默认行为、作用范围和删除条件；不能把关闭 UI 当成撤销已经发生的数据或外部副作用。

阈值、观察窗口和负责角色来自项目目标/约定，没有时提出可讨论方案，不虚构“已批准”标准。健康探针正常还需结合受影响的用户行为、错误率或数据一致性信号。

## 执行与恢复

执行前确认目标环境、版本、已有授权、前置检查以及真实恢复路径。准备任务可以完成配置/脚本和安全演练；外部上线按实际授权执行，不因技能命中自动获得权限。

结果不明时先查询部署/操作状态，再决定是否重试。执行一个会重复产生副作用的命令前，必须知道去重或恢复语义。失败达到项目停止条件即暂停后续批次，实施已授权恢复或交付明确处置建议。

交付实际制品、环境、执行结果、验证信号与剩余动作。冒烟通过说明发布后的有限行为正常，不能证明所有用户情境或长期可靠性。
