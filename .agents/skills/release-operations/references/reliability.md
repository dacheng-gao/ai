# 面向用户结果的可靠性

依据 Google SRE 公开章节、Majors 等《Observability Engineering》、Brendan Gregg 的性能诊断方法与 Sidney Dekker 的系统安全复盘视角，按当前服务规模裁剪。无需照搬大型公司的团队结构、数值目标或全部运维机制。

## 定义少量有用的 SLI 与 SLO

从关键用户任务出发选择指标：请求能否成功、多久完成、数据是否新鲜或完整。说明有效事件、好事件、测量位置、时间窗口、排除项和分群；服务器返回成功不一定等于用户任务完成。

SLI 是测量口径，SLO 是目标，SLA 是带约定后果的服务协议。已有承诺优先；未知时提出目标候选及依据，不擅自承诺可用性。

计数型成功率目标的错误预算可按适用事件总数乘以允许失败比例表达；时间型目标使用一致时间口径。不要把请求数预算与停机分钟混用。预算消耗可以指导变更节奏和可靠性投入，但自动冻结发布必须有已批准政策，不能由 agent 自行设立。

检查聚合是否掩盖少量用户或高价值流程的失败；低流量时百分比波动大，不能仅凭短窗口归因。避免为所有可测指标设服务目标。

## 观测与告警

- **监控 vs 可观测性（Observability Engineering）**：传统监控靠预聚合指标与固定仪表盘回答“已知的未知”（如 CPU 是否超阈值）；复杂线上故障往往是“未知的未知”（只影响某租户、某版本或某参数组合），需要**高基数、高维度的结构化宽事件（Structured Wide Events）与分布式追踪**支持事后任意切片下钻。关联标识帮助串联一次请求，但事件和日志必须避免记录机密或不必要个人数据。观测数据缺失应称为盲区，不能据此推断服务正常。
- **快速诊断信号框架**：排查性能或可用性异常时，优先从两套低噪音视角切入，避免漫无目的翻日志：
  - **请求驱动服务（黄金信号 / RED）**：流量速率（Rate/Traffic）、错误率（Errors）、耗时分布（Duration/Latency，优先看 P95/P99 而非均值）、饱和度（Saturation）。
  - **底层资源（USE，Brendan Gregg）**：对 CPU、内存、磁盘、网络、连接池、线程池、队列逐项看使用率（Utilization）、饱和度（Saturation，排队长度）和错误（Errors）。

告警应关联用户影响或需要及时行动的风险，并有可执行处置路径。消除重复与无行动价值的噪声，区分需立即响应和可排期处理的问题；不以告警数量证明可靠性。

## 故障响应

先确认影响、范围和起始时间，结合变更记录、日志及指标建立候选解释。按能区分解释的证据选择下一步观察，不因故障恰好发生在发布之后就断言发布是唯一原因。

恢复优先：依据已知状态与授权选择回退、隔离、降级、扩容或向前修复。不能套用通用动作，例如数据库连接已饱和时扩容应用可能放大压力。每次动作保留时间、目标、观察和后果。

与人协作需要明确当前协调者和交接状态，但不虚构值班人或自动发送通知。请求本身为日志分析时给出诊断和验证路径，不越权控制服务。

## 无责复盘与消除重复劳动

对达到项目复盘条件或用户要求的事故，整理影响、时间线、触发因素、放大因素、发现/恢复过程和证据。遵循系统安全的新视角（Sidney Dekker）：**“人为失误”是系统深层脆弱性的症状，而不是调查的终点或根因**。按**局部理性（Local Rationality）**还原当事人在当时的信息、告警、工具界面和时间压力下为何认为该操作合理，据此改进护栏、默认值、可观测性与恢复工具，而不是止步于归责个人。

每项必要改进要说明减少哪类故障、怎样验证效果，沿用真实负责人与跟踪系统；没有人员分配时标待分配，不杜撰。避免一律“加强培训”或“全部重写”。复盘文档完成不意味着预防措施已生效。

找到重复、手工、可自动化且随规模增加的运维劳动，评估自动化本身的维护和失败成本。优先减少噪声、等待与频繁中断；不为追求自动化率引入更难维护的系统。
