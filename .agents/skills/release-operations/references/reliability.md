# 面向用户结果的可靠性

依据 Google SRE 公开章节，按当前服务规模裁剪。无需照搬 Google 的团队结构、数值目标或全部运维机制。

## 定义少量有用的 SLI 与 SLO

从关键用户任务出发选择指标：请求能否成功、多久完成、数据是否新鲜或完整。说明有效事件、好事件、测量位置、时间窗口、排除项和分群；服务器返回成功不一定等于用户任务完成。

SLI 是测量口径，SLO 是目标，SLA 是带约定后果的服务协议。已有承诺优先；未知时提出目标候选及依据，不擅自承诺可用性。

计数型成功率目标的错误预算可按适用事件总数乘以允许失败比例表达；时间型目标使用一致时间口径。不要把请求数预算与停机分钟混用。预算消耗可以指导变更节奏和可靠性投入，但自动冻结发布必须有已批准政策，不能由 agent 自行设立。

检查聚合是否掩盖少量用户或高价值流程的失败；低流量时百分比波动大，不能仅凭短窗口归因。避免为所有可测指标设服务目标。

## 观测与告警

按任务连接指标、日志和追踪；关联标识帮助解释一次操作，但日志避免记录机密或不必要个人数据。观测数据缺失应称为盲区，不能据此推断服务正常。

告警应关联用户影响或需要及时行动的风险，并有可执行处置路径。消除重复与无行动价值的噪声，区分需立即响应和可排期处理的问题；不以告警数量证明可靠性。

## 故障响应

先确认影响、范围和起始时间，结合变更记录、日志及指标建立候选解释。按能区分解释的证据选择下一步观察，不因故障恰好发生在发布之后就断言发布是唯一原因。

恢复优先：依据已知状态与授权选择回退、隔离、降级、扩容或向前修复。不能套用通用动作，例如数据库连接已饱和时扩容应用可能放大压力。每次动作保留时间、目标、观察和后果。

与人协作需要明确当前协调者和交接状态，但不虚构值班人或自动发送通知。请求本身为日志分析时给出诊断和验证路径，不越权控制服务。

## 无责复盘与消除重复劳动

对达到项目复盘条件或用户要求的事故，整理影响、时间线、触发因素、放大因素、发现/恢复过程和证据。区分事实与原因假设，不止于“某人操作失误”，继续检查当时信息、工具和流程如何促成行为。

每项必要改进要说明减少哪类故障、怎样验证效果，沿用真实负责人与跟踪系统；没有人员分配时标待分配，不杜撰。避免一律“加强培训”或“全部重写”。复盘文档完成不意味着预防措施已生效。

找到重复、手工、可自动化且随规模增加的运维劳动，评估自动化本身的维护和失败成本。优先减少噪声、等待与频繁中断；不为追求自动化率引入更难维护的系统。
