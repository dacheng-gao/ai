# 业务数据库设计

让数据结构准确表达业务事实，让约束和事务维护事实的正确性，让查询与写入成本能用证据检验。按当前请求裁剪工作；局部评审无需重建整个数据库。

本技能综合关系模型、规范化、业务驱动的表设计、SQL 反模式和面向负载的物理设计方法。它不是各书的逐章摘要；方法来源和核实边界见 [sources.md](references/sources.md)。不编造原文、页码、作者观点或性能测量。

## 边界与入口

- **新设计**：从确认的业务模型与使用场景进入，形成逻辑模型，再选择数据库实现。
- **评审**：用实际场景、DDL、查询、事务与运行证据寻找信息丢失、非法状态或不必要成本；保留现有兼容要求，只改有依据的部分。
- **实施**：只有请求已授权实施时才写 DDL、代码或迁移。设计或评审不自动授权连接生产库、改数据、安装扩展、发布或提交。

业务语义尚未明确时，先补足影响存储的身份、关系、历史与不变量；需要深入业务分析时，可配合已有的业务建模技能。不要从现有表反推出“已确认需求”。本技能负责语义到存储的映射，不另立业务事实来源，也不绑定 ORM、语言或迁移工具。

先检查已有修改、相关项目规则、业务来源、现有 schema/迁移及实际数据库产品、主版本、扩展与权限。工具可核实的未知先查明；版本未知时给逻辑设计并标注待核实能力，不能默认 PostgreSQL 最新版或悄悄替换用户选定的数据库。

## 形成足够的设计依据

把已确认事实、当前实现、提议和未知分开。只补足会改变当前决定的输入：

- **业务**：一行代表什么，如何识别同一对象，关系的基数和可选性，什么必须持续成立，何时允许修改、撤销或删除。
- **时间**：要保存当前事实、当时事实、变化记录还是生效区间；纠错与迟到记录如何解释。
- **读取**：真实 SQL 或访问场景、筛选与连接、排序、分页、聚合、返回列、频率和新鲜度要求。
- **写入**：新增/更新/删除模式、批量与重试、同一对象的竞争、事务跨度、哪些字段常变。
- **规模与运行**：量级、增长、分布与热点、保留期，以及已有性能目标、运行指标和环境限制。

没有性能目标或数据分布时，不虚构 QPS、百分位或容量指标。先交付有边界的候选设计和验证方案。身份、唯一范围、历史口径或严格一致性等未知若改变正确性且无法查明，集中问一个问题，继续不依赖答案的部分。

## 从模型到数据库

### 1. 先表达事实与不变量

对涉及的表说明行的粒度、业务含义、身份、所有者、关系与生命周期。一张表可以表达实体、关系、发生的事实或快照；领域对象、聚合、类、页面与表没有一对一对应要求。

明确候选键、唯一范围和函数依赖；代理主键不能替代业务唯一性。用插入、更新、删除反例检查冗余、信息丢失与非法组合。需要逻辑模型取舍时读 [logical-model.md](references/logical-model.md)。

以消除更新异常的规范化结构为起点。拆分须保持无损连接，并检查依赖能否有效维护；不是把范式等级当目标。引入冗余前写明原始事实、派生规则、维护责任、原子性/新鲜度、重建与核对方式。表达“成交时价格”的快照与重复保存“当前价格”是不同事实。

### 2. 决定每条规则由什么机制保证

将关键不变量映射到可执行机制：类型、非空、唯一、检查、外键、排斥约束，以及需要的事务协议。给数据库可表达且应持续成立的规则建立约束，应用验证用于友好反馈，不能独自承担并发正确性。

精确区分 SQL NULL、空串、仅空白、零值和缺失；“非空”不自动说明允许哪几种。若说明承诺拒绝空串，NOT NULL 本身并不实现该承诺；按目标产品的比较/长度语义选择相应检查，也不能未经业务依据拒绝空白或零值。

跨行、跨表或跨系统规则不能伪装成普通行检查。明确所有写入口、需要协调的记录、锁/隔离与失败恢复；选择触发器时也须分析其并发协议。读写分离、缓存和异步投影不得降低已确认的一致性要求。

按所选产品、版本与运行权限核实实现，只加载当前产品的参考：

- PostgreSQL：[postgresql.md](references/postgresql.md)。
- MySQL/InnoDB：[mysql.md](references/mysql.md)，不要默认兼容产品/MariaDB 行为相同。
- SQL Server：[sql-server.md](references/sql-server.md)，同时确认版本、edition、兼容级别及快照设置。

选能简化当前问题的能力，并说明代价；不因可用就堆叠扩展、分区、JSON 或触发器。同名类型、唯一性、隔离级别、upsert 和在线 DDL 不代表跨产品同义；从通用模型重新推导目标实现，不能做语法替换式移植。

### 3. 把竞争写成事务协议

围绕业务操作描述：读取条件 → 竞争裁决 → 修改事实 → 原子提交 → 冲突/重试/回滚语义。区分丢失更新、写偏斜、重复意图和合法业务拒绝；不要只写“加事务”或“使用乐观锁”。

单行条件更新适用时，让资格检查与修改在同一语句完成，并检查影响行数。跨行规则可选择共同锁定的稳定记录、已证明有效的约束或可串行化事务；检查幻影、空结果与所有写入口。锁不到不存在的行，也不能靠逐行锁保证集合级规则。

重试须从新的事务开始，范围包含整个业务操作，次数有界，外部副作用可去重。幂等键的作用域、请求是否相同、竞争及提交后的结果必须明确；唯一键或 `ON CONFLICT` 本身不是完整幂等协议。

### 4. 用真实负载选择物理结构

为重要查询或写路径建立简短的访问记录，把索引候选关联到实际谓词、连接、排序及完整性检查；同时说明插入、更新、删除、存储和维护代价。使用 [workload-and-verification.md](references/workload-and-verification.md) 处理索引、读写权衡与验证。

先检查主键/唯一约束及已有索引能否覆盖需要。外键引用端索引按连接、父记录变更和数据量判断；不为每个字段或每个外键机械新增索引。索引列顺序不以“选择性最高先放”一概决定。

只有证据表明基础查询、索引与事务设计不足时，才讨论反规范化、投影、缓存、分区或复制；这些选择分别说明一致性和运行成本，不能代替修复错误模型。

## 验证与交付

验证结构能保存合法业务事实，并拒绝相关非法事实。按风险选择必要检查：

- 合法、边界与违反例；NULL、重复键、作用域、删除/撤销和历史变化。
- 涉及竞争时，使用独立数据库会话交错操作，验证提交后的不变量、失败及重试行为。单会话成功不能证明并发正确。
- 涉及性能时，在有代表性的分布和写入竞争下比较结果正确性、执行计划、延迟、写成本与维护成本；没有实际负载时仅报告候选方案。
- 演进已有 schema 时，检查旧数据、兼容窗口、回填、锁、验证、失败恢复与切换；具体迁移由项目的迁移流程处理。

可参考 [worked-example.md](references/worked-example.md) 的业务到 DDL 演练及可执行样例；这些是假设性教学场景，不能作为项目业务事实。

输出满足当前请求的最小设计：表与业务模型的对应解释、关键键/关系/约束、事务协议、重要查询与索引的依据、演进影响、验证证据和未决项。表较多时用 ER 图或关系表，图不能替代规则与事务说明。评审先报告具体问题、触发场景、后果和建议；不要仅罗列通用检查项。

交付前把设计说明中承诺的保证逐项对照 DDL、事务协议与验证预期；说明由哪一层负责，缺少实现的保证保持待实施/未验证。

当设计已能解释约定业务、落实关键不变量、支持已知访问路径并明确剩余风险时收敛。分别报告实际执行、场景推演与尚未验证的结论；不得把 DDL 可执行、命中索引或一次样本测量称为已证明生产正确性或性能。
