# 从业务模型到关系模型

在身份、关系、表拆分、历史或规范化需要实质决定时读取。先用业务规则确定可保存的信息，再决定存储形式。

## 行的粒度与键

能用一句话说明一行是什么：一个对象、一次事实、一个关系的有效期、一个明细项或某口径的余额。把不同粒度混在同一行，常导致重复、空字段和错误聚合。

- 对象的技术 ID、外部编号与业务识别键分别处理。代理键稳定便于引用，但业务规则要求的候选键仍应约束。
- 编号在哪个组织、仓库、时间或来源内唯一，以确认的规则决定；不要因为用了 UUID 就取消范围约束。
- 若租户/组织隔离是需求，关系也需保持该范围。两个独立外键只能证明双方分别存在，不能证明同属一个范围；考虑包含范围的复合外键及对应候选键。
- 候选键是否允许 NULL，比较是否区分大小写、空白、排序规则，以及编号能否复用，都会改变“相同”的含义。
- 明细的业务身份可能是行号或独立 ID。“订单 + 产品”只在同一产品禁止重复出现时才是正确键。

## 关系与边界

多对多关系若有数量、角色、生效期或价格，就是需要明确粒度和约束的事实，不是没有含义的中间表。

一对一可用唯一外键表达，但是否拆表还取决于可选性、生命周期、权限、宽度与修改热点。关联存在不代表可以级联删除；独立对象、历史凭证和拥有式明细需要不同删除语义。

“一个父对象至少有一条明细”与“每条明细都有父对象”不是同一约束。普通外键只保证后者；前者需在可提交边界与所有删除/移动入口维护。不要因为事务中有短暂空集合就拒绝合法操作，也不要把事务中的临时态长期暴露出去。

业务类型确有公共身份和共同行为时，比较单表、共享主键的类型表或独立表。单表要约束类型与专属字段的合法组合；类型表要维护完整性和互斥/重叠规则；独立表要接受跨类型关联的限制。不要默认用 `(object_type, object_id)` 实现可引用任意表的外键。

树结构按操作选邻接关系、闭包表或路径等方案；节点外键不防环，不保证同一作用域。闭包和路径的更新责任、并发与重建成本必须明确，不因需要树就预建全部结构。

## 函数依赖与规范化

从业务语义判断 `X → Y`：对于允许的全部事实，相同 X 是否必须有相同 Y？样本中恰巧相同不是依赖，代理键决定所有字段也不能消除业务字段间的其他依赖。

把重复集合移到适当粒度，再检查候选键的部分依赖、非键间传递依赖与多个独立集合的交叉重复。通常以 3NF/BCNF 的思路消除更新异常；无损连接、依赖保持和有效约束比追求更高范式重要。BCNF 分解可能不保持全部依赖，必须评估维护方式；更高范式只在真实的多值/连接依赖出现时分析。

对每次拆分，用例验证：能否不丢信息地还原原事实？会不会产生原本不存在的组合？重要规则能否由局部约束维护，还是增加跨表协调？对每次合并，检查是否产生重复事实、非法 NULL 组合或不同生命周期的耦合。

## 当前事实、历史与派生事实

先确认问题是“现在是什么”“当时确认了什么”“什么时候变了”还是“在什么区间有效”。仅加 `created_at/updated_at` 不能表达这些全部含义。

- **快照**：当时的地址、名称或成交价格如果是业务事实，保留快照有独立语义；不能随主数据变化自动覆盖。
- **历史**：修订、撤销、事件、版本行与生效区间各有不同查询和纠错语义；按需要选择，不默认事件溯源或双时态。
- **区间**：明确端点开闭、相邻是否冲突、空区间/无界区间是否合法，以及采用业务时间还是记录时间。
- **派生值**：计数、金额汇总或余额说明源事实、口径、舍入和更新时间。只读计算、同事务维护或允许延迟的投影，各有成本。
- **冗余**：要有唯一维护者、故障/重试行为、核对与重建途径。“之后同步”不足以维护严格不变量。

状态列适合表达当前生命周期，但合法值检查不等于合法流转。迁移前提需在竞争裁决时检查；从旧状态更新到新状态的条件更新可防止重复流转。多个状态维度是否独立应由业务判断。

## 数据含义与常见反模式

| 结构或做法 | 先检查的实际问题 | 有依据的选择 |
|---|---|---|
| 逗号分隔 ID、数组存关系 | 元素是否需要外键、独立属性、修改和查询 | 独立关联行；数组可用于真正作为一个值处理的集合 |
| 万能 EAV/JSON 表 | 类型、键、关系和规则是否已知且稳定 | 核心事实用明确列/表；确有动态属性时限定词汇、类型和查询能力 |
| 万能多态引用 | 是否能拒绝不存在或错误类型的目标 | 明确关系表、类型结构或有证明的统一身份模型 |
| 每个页面一张事实表 | 是否重复保存同一业务事实 | 共享事实，通过查询/视图表达不同投影 |
| 全部字段可空/空串默认 | 未知、不适用、未发生是否混淆 | 明确缺失语义；必要时拆分可选事实，避免伪造默认值 |
| 所有关系级联删除 | 独立对象或历史是否被误删 | 按生命周期指定限制、级联、撤销或保留 |
| 统一软删除 | 唯一键复用、引用、历史、查询漏筛 | 仅在需求成立时采用；定义恢复、引用和合法活跃范围 |
| 先加表再补业务含义 | 表粒度和规则是否无法解释 | 回到具体场景，确认事实与不变量 |

这些是风险入口，不是禁止清单。动态属性、冗余和软删除各有合理用途；判断依据是业务语义、维护能力和真实负载。
