# 内部架构、耦合均衡与务实演进

仅在评审或设计代码库内部架构（模块/包划分、依赖方向、分层深度、核心逻辑与 I/O 边界、耦合重构优先级或设计模式取舍）时读取。综合 Vlad Khononov《Balancing Coupling in Software Design》、Yourdon/Constantine《Structured Design》、Alistair Cockburn 六边形架构、Robert C. Martin《Clean Architecture》、Gary Bernhardt《Boundaries》、Mark Richards/Neal Ford《Fundamentals of Software Architecture》、Adam Tornhill《Software Design X-Rays》、Gamma 等《Design Patterns》与 Martin Fowler 公开文章；核查范围见 [来源映射](../../software-delivery/references/sources.md)。

## 用三维模型科学判断耦合（Khononov & Constantine）

耦合不是非黑即白的坏事——系统必须通过耦合协作。不要喊“彻底解耦”，而应结合三个维度做判断：

1. **整合强度（共享了多少知识）**：从强到弱依次为 侵入式（直接访问对方内部结构/共享表）→ 功能式（共享同一业务规则的多个副本）→ 模型式（共享领域数据结构）→ 契约式（仅依赖精简、显式定义的接口契约）。
2. **距离（跨越的边界成本）**：同文件/同类 < 同模块/包 < 跨包/跨库 < 跨进程/跨团队服务。
3. **变化频率（Volatility）**：上游知识或实现多久改变一次。

按平衡原则裁决：

| 组合形态 | 诊断结果 | 正确动作 |
| --- | --- | --- |
| **高强度 + 近距离** | **高内聚（健康）** | 保留在一起；经常一起变化的代码本就应该相邻 |
| **高强度 + 远距离 + 高变化** | **脆弱架构（痛点）** | **降低整合强度**（改用窄契约/适配器隔离）或**缩短距离**（合并到同一模块内） |
| **高强度 + 低变化** | **可接受（低风险）** | 若上游极其稳定（如标准库、长期冻结的协议），不必为“理论上解耦”额外包一层 |
| **低强度（多层接口）+ 低变化** | **过度设计（偶然复杂度）** | 删除多余抽象层与透传接口，让代码回归直接清晰 |

## 内部代码架构与依赖方向（Hexagonal / Clean / Functional Core）

良好的单应用内部架构关注两件事：**把易变的技术细节挡在业务核心之外**，以及**让一次业务改动落在尽量少的目录里**。

1. **业务核心与 I/O 边界分离**：
   - **函数式核心，命令式外壳（Gary Bernhardt）**：将复杂计算、资格判断、状态推导写成无 I/O 副作用的纯逻辑核心；由薄的外壳负责读库、调外部接口、写库并传入/传出数据。这样核心规则无需 mock 数据库就能高速单测。
   - **端口与适配器（Alistair Cockburn 六边形架构） / 依赖原则（Clean Architecture）**：当核心需要调用外部能力（支付、发信、外部搜索、可替换存储）时，由核心定义表达业务意图的**端口（接口/函数签名）**，外部适配器实现它并向内依赖。框架、HTTP DTO 与数据库行结构停留在适配器层，不渗透进核心模型。
   - **反仪式化护栏**：简单 CRUD、只读报表或无复杂策略的胶水代码，直接用清晰模块操作存储即可；**不要**机械照搬四五个同心圆层或给每个类建同名 `*Interface` + `*Impl`。
2. **依赖结构硬规则（Clean Architecture 组件原则）**：
   - **无环依赖（ADP）**：模块/包之间的依赖图必须是有向无环图（DAG）；出现 A ↔ B 环时，要么提取共同依赖的稳定底层概念，要么倒置其中一方的依赖。
   - **稳定依赖（SDP）**：让高变化的上层特性依赖低变化的稳定核心，绝不让稳定核心反向依赖某个具体页面、控制器或易变渠道。
3. **按业务能力分包优先于按技术层平铺（模块化单体）**：
   - 当模块增多时，优先按业务能力/垂直切片组织目录（如 `billing/`、`fulfillment/`、`identity/`），对外只暴露明确入口，隐藏内部子模块；避免把整个系统按技术角色横向摊平为巨大的 `controllers/`、`services/`、`repositories/`，导致改一个小需求要横跨全部目录且所有内部细节彼此可见。

## 用证据驱动演进，拒绝盲目重做（Tornhill & Fowler）

- **设计耐力权衡（Fowler Design Stamina Hypothesis）**：完全不设计会在短期后迅速失速，而提前过度设计会在当下就拖慢交付。正确位置是**刚好能维持清晰边界与低修改摩擦的最小好设计**——随着需求增长持续小步演进，而不是一次性设计“终极架构”。
- **基于历史证据选重构目标（Adam Tornhill《Software Design X-Rays》）**：在已有代码库评审架构时，优先结合 Git 提交历史而不是只凭静态直觉：
  - **热点（Hotspots）** = 复杂度高 × 修改频率高：设计投入回报最高，应优先解耦与模块化。
  - **变更耦合（Change Coupling）** = 没有显式 import 却反复在同一提交里一起修改的文件：往往暴露了隐蔽的知识重复或错误的边界切分。
  - **冷区代码**：复杂但长期不动的代码利息极低，若与当前任务无关，不要为了“架构整洁”主动重写。

## 务实使用设计模式（GoF）

设计模式是**已验证的局部结构解法**，不是优良设计的评分项：

- 优先**对象组合**而非类继承；在真实变化点面向窄接口编程。
- 只在观察到**真实结构张力**时引入对应模式：已有 2+ 种实际并行策略且分支持续增长 → `Strategy`；需要隔离不稳定第三方协议或遗留接口 → `Adapter` / `Facade`；生命周期状态流转使条件判断纠缠不清 → 显式状态转换表或 `State`。
- 警惕模式滥用：只有单一实现却上 `AbstractFactory`、`Builder`、`Visitor` 或泛化事件总线，通常属于投机性过度设计，应直接化简为普通函数或结构。
