# 模块边界、契约与公共 API 设计

仅在设计公共 API、梳理跨模块契约、评估抽象或继承结构，或评审接口演化风险时读取。综合 Parnas（1972）、Bertrand Meyer《Object-Oriented Software Construction》、Joshua Bloch《How to Design a Good API and Why It Matters》与 Sandi Metz《Practical Object-Oriented Design》（第 2 版）的公开原则；核查范围见 [来源映射](../../software-delivery/references/sources.md)。

## 秘密列表：验证模块拆分是否隐藏了变化（Parnas）

David Parnas（1972）提出，模块划分的依据是**封装可能变化的困难设计决策（“秘密”）**，而非程序执行的先后步骤。评审拆分方案时做一次快速检查：

1. 列出当前涉及的 2–5 个可能变化的决策（如存储表结构、第三方协议、计费策略、序列化格式、并发控制机制）。
2. 检查每个决策是否**仅由单个模块知道**。如果改一个协议或表结构需要同时改三个模块的内部逻辑，说明拆分是按时间顺序而非按秘密进行的，存在信息泄露。

## 契约式设计与命令查询分离（Meyer & LSP）

- **明确契约三要素（Design by Contract）**：
  - **前置条件（Precondition）**：调用方必须满足的前提（如已认证上下文、非负数量）。
  - **后置条件（Postcondition）**：调用成功后模块承诺达成的状态或结果。
  - **不变量（Invariant）**：模块在每次公开操作前后必须始终维持的合法状态。
  契约明确了“谁负责校验”：信任边界之外的输入用显式错误处理校验；内部可信契约由类型、前置条件或断言表达，避免每层重复做含义模糊的防御性判空。
- **命令查询分离（CQS）**：一个方法要么是**查询**（返回数据、无外部可观察副作用），要么是**命令**（改变状态）。查询可被安全地重复调用或重排而不改变系统状态；确需混合的原子操作（如 `pop`、CAS 更新、创建并返回 ID）应在命名和文档中明确其副作用。
- **行为可替换性（LSP）与组合优于继承**：任何实现或子类型必须遵守父契约——不得**加强前置条件**、不得**削弱后置条件**、不得破坏不变量或抛出契约外的新异常类型。复用行为时默认优先对象组合与清晰接口，仅在稳定的“is-a”行为契约成立时使用继承。

## 公共 API 设计准则（Joshua Bloch）

公共 API（对外 HTTP/RPC、SDK、跨模块共享包）一旦发布几乎不可撤回，改变成本远高于内部实现：

1. **有疑问时就先不暴露（When in doubt, leave it out）**：以后随时可以新增接口、字段或参数，但极难删除或改语义；先保持最小概念面。
2. **最小惊讶原则**：命名、参数顺序、返回约定和边界行为与语言生态及同库已有接口一致，不要让调用方靠猜。
3. **尽早暴露错误（Fail Fast）**：能靠静态类型阻止误用的（如用专用类型代替连续多个 `string`/`boolean` 参数），不留到运行时报错；运行时非法参数在入口处立即拒绝，避免把坏状态带入深层再延迟崩溃。
4. **最小可变性与清晰所有权**：避免返回内部可变集合的直接引用，也不在未声明的情况下就地修改调用方传入的对象。
5. **不让调用方做模块自己能做的事**：消除样板代码与隐含调用顺序，把复杂度留在模块内部。

## 识别并纠偏错误抽象（Sandi Metz）

- **重复比错误抽象更便宜**：当两段相似代码已经开始各自演化，强行共用一个带满布尔标志位和分支的“通用函数”只会放大耦合。
- **纠偏路径**：发现抽象已经变成满是特例参数的浅壳时，不要继续往里加开关；先把共用逻辑**内联回各调用方**，看清各自真实的最小需求，再只抽取真正稳定的共性。
- **控制依赖穿透（迪米特法则）**：避免跨多层连续导航内部结构（如 `order.customer().billing().taxRate()`），改由直接协作者暴露有业务含义的查询或动作。
