# Markdown 与编辑质量

目标是让内容易读、易查、可维护；先遵循现有模板和目标渲染器。默认采用常见 Markdown/GFM 的可移植写法，不引入 Obsidian 双链、专有 Callout、HTML 布局或 MDX 组件，除非环境支持且任务需要。

## 先内容与逻辑，后版式

- 开头提供读者当前最需要的信息；段落围绕主要意思展开，句间说明必要的因果、条件和转折。
- 标题描述主题或行动，层级连续；不要用加粗冒充标题。文档通常一个一级标题，但保留已有集合式文档约定。
- 程序步骤用有序列表，并列项用无序列表；解释和论证优先连贯段落，避免每句话都变成项目符号。
- 表格用于同维度比较和结构化查询。多段步骤、长论证或多重嵌套改成小节；使用标准表格语法，不用空格模拟无分隔符的表格。
- 保留有用的例外、限制和不确定性；删去套话、重复概述、无证据形容词和对写作过程的讲述。不要为“去 AI 味”改变技术含义。

## 中文与术语

用自然、直接的中文，不照搬英语句长、大小写或标点规则。需要保留的专业术语首次出现时说明中文含义或缩写；后续保持一致。项目有词汇约定时优先采用。

中文正文通常用中文标点，中英文和数字间按项目惯例留空格；代码、路径、API 字段和引用原文保持原样。不把 ASCII 代码引号换为弯引号，不将 `snake_case` 标识符译成中文。

一句表达主要意思，但保留必要关系，不机械切成碎句。专业不等于官样表达：例如把“完成相关配置工作后即可进行服务启动操作”改为“配置完成后启动服务”；不删掉实际前置条件。

## 表格自检与格式化

完成本次涉及的表格后，整理其 Markdown 源码，使列边界整齐且渲染含义不变。只处理新写或修改的实际表格，不顺带格式化无关表格、代码围栏或缩进代码块中的示例；仅评审时给出问题。

### 稳定的处理流程

为避免不同执行轮次产生不一致结果，按以下固定流程处理：

1. 逐行扫描文档并跟踪 fenced code block 状态；代码围栏内的内容永远不作为表格处理。
2. 将每个连续表格解析为单元格矩阵，确认表头、分隔行和数据行的列数一致；单元格内的转义竖线（`\|`）不算列分隔符。
3. 对每列计算所有单元格的最大显示宽度（中文宽字符按 2 列计算），按该宽度补齐每一行；表头和分隔行也使用同一列宽。补齐时必须按“目标显示宽度 - 当前显示宽度”添加空格，不能使用按 Unicode code point 数量补齐的 `len`/`ljust` 逻辑。可复用以下定义：`display_width(s) = Σ(2 if east_asian_width(c) in {W,F,A} else 1)`，`pad(s,n) = s + ' ' * (n - display_width(s))`。
4. 重新生成标准 GFM 行：每个单元格边界保留一个空格，分隔行每列至少 3 个连字符，并保留原有的左、中、右对齐标记。
5. 重新解析生成结果，逐行检查列数、边界空格和分隔行合法性；再比较格式化前后的单元格文本、链接、转义内容和表格外文本，确保只改变空白。

没有现成 formatter 时，应使用可重复运行的临时脚本完成上述步骤，并在交付前至少执行一次“格式化后再格式化”的幂等性检查：第二次运行不得产生差异。

验收样例必须至少包含一张中英文混排表格（例如 `数据库`、`nvarchar(50)` 和英文长标识符混合），并逐列断言表头、分隔行和每个数据行的 `display_width` 相同。仅断言 `len(row)` 相同不构成通过。

- 优先采用项目已有格式化工具及配置，并限制到授权范围；工具会改动整文件时检查差异，避免覆盖无关修改。没有现成工具时直接整理，不默认安装依赖或创建通用格式化脚本。
- 无项目约定时使用首尾竖线，单元格内容两侧至少留一个空格；按每列最长源码显示宽度补空格，统一该列的竖线位置。中英文混排按等宽显示宽度考虑中文宽字符，不仅计算字符个数；组合字符、emoji 和字体可能影响显示，以项目工具结果为准，不承诺所有编辑器像素级对齐。
- 表头、分隔行与数据行应对应相同列数。保留分隔行原有的左、中、右对齐冒号，每列使用至少三个连字符，按需补齐宽度。保留空单元格；列数异常时先查遗漏或未转义竖线，不凭猜测丢弃、合并数据或补写业务内容。
- 区分列分隔符与单元格内的转义竖线（如 `\|`），不能直接按所有竖线切分。保持行内代码、链接、转义、行顺序和单元格文本不变，只调整表格边界空白及分隔行；不能为缩窄列而截断内容或改变代码中的空格。
- 格式化后对比前后单元格内容、列数、对齐方式和表格外文本；如有可用渲染或文档检查工具，确认结构有效。源码对齐和语义正确分别核对，不能将补齐空格当成渲染已验证。

## 代码、链接与图

- 标题、列表与围栏前后留空行；围栏标注语言，示例中展示围栏时外层使用更长围栏。注意列表内缩进和表格中的竖线转义。
- 命令与预期输出分开，标清占位参数及需替换项；多行命令的续行符与 shell 一致。
- 链接文字说明目标；仓库文档使用可迁移的相对链接，不把本机绝对路径写入团队文档。复核文件、锚点和重命名后的引用。
- 只有图能减少理解成本时才添加。关系图、时序图、状态图选其一或少量组合，图中状态和名称必须与正文一致。
- Mermaid 仅用于支持的渲染器；无法确认支持时保留文字等价说明或采用项目已有图形形式。图未渲染验证时不声称渲染通过。
- 图片提供有意义的替代文本，证据截图需与说明版本相符。表格不能只靠颜色表达状态。

## 按用途验证

实质性文档改动依次检查：结论是否有依据；章节、表格、图和示例是否矛盾；读者是否缺前提或判定方法；链接与渲染是否可用。已有 markdownlint、文档构建或链接检查能覆盖的部分复用即可。

没有现成工具时检查源文件并明确渲染或命令尚未验证，不默认增加依赖或把所有 lint 风格偏好变成业务验收条件。

长文可添加目录和必要元信息，短文直接表达。自动生成区与手写区分开维护，不直接覆盖用户注释。共享契约避免无必要复制；需要保留快照时标出适用版本和来源。
