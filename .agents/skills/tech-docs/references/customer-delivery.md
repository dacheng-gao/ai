# 客户交付与使用文档

先确定读者是客户操作员、客户管理员、集成开发者还是验收人员，以及产物是手册、交付清单、验收方案或交付报告。客户读者需要完成工作所需的信息，技术深度随角色变化；不默认隐藏集成所需细节。

## 交付清单与边界

按已有合同、批准范围和实际交付证据列出产物、版本或可识别构建、用途、获取位置、依赖及交付状态。区分“拟交付”“已提供”“待验证”“已验收”；状态需有依据。

仅在有来源时写负责人、交付日期、支持渠道、响应时限、SLA、培训安排、承诺或签署记录。缺失的信息明确待补，不用看起来真实的占位人名或链接。

## 使用与运维手册

围绕客户任务组织：用途与适用对象、开通或安装前提、最短使用路径、预期结果、常见问题与实际支持入口。解释第一次出现的术语；客户不需读源码才能完成操作。

- 步骤写清账号角色、入口和输入；截图必须与版本匹配，缺图时不要编造图中内容。
- 初始凭证说明使用授权渠道获取，不写入真实密码、Token 或个人数据。
- 风险提示说明触发条件、后果及必要防范，放在操作前；不堆砌通用免责文字。
- 管理员文档按适用性补充备份、恢复、升级和数据导出；成功判据与恢复限制要可查。

## 验收方案与报告

方案将约定范围映射到验收步骤、环境、输入和可观察标准。报告另列实际执行证据、差异与未解决问题。交付软件不等于性能验证、业务认可或正式签收。

可裁剪结构：“交付概况 → 产物与版本 → 部署/使用 → 验收依据与状态 → 已知限制与后续事项”。短交付邮件只需关键产物、影响和下一步，不强制使用这份完整结构。

交付前检查：内部路径是否被误当成客户可访问地址？示例数据是否虚构且标明？客户承诺是否有依据？正文是否泄露与客户任务无关的内部记录？文档生成不触发发送或签署。
