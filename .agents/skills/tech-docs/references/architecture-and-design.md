# 技术架构与方案设计

先辨别产物：现状架构解释已有系统；技术方案提出实现某目标的选择；ADR 记录一个决定及后果。不要将三者混写成已落地事实。

## 按决策需要取用的内容

- 背景与驱动：具体问题、现状证据、目标和不涉及的范围。质量要求应落到场景，例如故障发生时哪些请求需要继续服务；没有依据不写可用性或性能数字。
- 边界与责任：系统外部参与者、模块职责、数据所有权和依赖。目录树不能替代责任模型。
- 关键流程：正常路径及关键失败路径；说明同步与异步边界、状态变化、事务边界。涉及重试时考虑幂等、重复、乱序和超时；仅在相关时展开。
- 契约：接口、事件、数据结构及兼容策略。区分拟议字段与已存在字段，避免示例被误认成正式协议。
- 权衡：真实可行方案、选择理由、代价、证据和会改变选择的假设。简单明确改动不制造多个备选方案，不默认采用微服务或复杂模式。
- 落地与验证：受影响组件、迁移先后、旧新版本共存、可观察信号、验证方式与恢复路径。数据变更要考虑旧程序能否读取新数据、回滚代码是否足够。

## 可裁剪结构

方案可组织为“问题与约束 → 建议与理由 → 关键设计 → 兼容与演进 → 验证及未决项”。
ADR 可组织为“状态 → 背景 → 决定 → 取舍与后果 → 关联证据”。没有决定就标为提案，不伪造批准者或日期。

## 交付前问题

实施者能否从文档知道谁负责什么、失败时发生什么、契约哪里变化？评审者能否辨认已证实的限制和未验证的假设？运维能否理解如何观察变更和恢复？

例如“失败自动重试”不够：已有资料若只确认最多三次，应写出这一限制，并将间隔、可重试错误和重复处理语义列为待确认；不能自行补成指数退避或恰好一次。
