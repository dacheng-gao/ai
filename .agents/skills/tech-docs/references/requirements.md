# 需求规格与验收标准

规格定义应有行为。现有代码可揭示现状和约束，但不能替代业务决策。使用材料中已有的编号、术语、角色和优先级；需要新编号时用局部稳定标识，不暗示已纳入外部系统。

## 组织行为

每个重要需求应能回答：谁在什么条件下，以什么输入或事件触发，系统必须产生什么可观察结果，哪些条件会阻止它？按适用性补充：

- 角色与权限：谁能查看、创建、修改、审批；越权行为的预期结果。
- 输入与约束：必填、合法范围、单位、默认值、唯一性、时间与时区；未确定值保留待确认。
- 状态与流程：前置状态、事件、后置状态、取消和恢复；并发或重复请求是否影响结果。
- 失败与异常：错误反馈、数据保留、补偿和再次操作的条件。
- 非功能要求：具体场景、指标依据和验证方法。不要把“快速”“安全”“易用”自行转换成数值承诺。

表格适合比较规则与字段；复杂流程用短段落或状态表，不把整份规格挤进一个超宽表。

## 可裁剪结构

“目的与范围 → 角色和关键流程 → 行为规则 → 数据与接口约束 → 验收标准 → 依赖及未决事项”。只需一条需求时直接写该行为及验收例子。

验收标准写可观察判断，可用 Given/When/Then，也可用普通条件句；不强制语法。标准应可追踪到需求，避免仅写“功能正常”“符合预期”。

## 保留未决事项的影响

示例：材料确认“管理员可禁用成员”，未说明是否立即撤销已有会话。可完成禁用入口、授权规则等已明确部分；将会话处理标为待确认，并说明它影响登录状态与验收用例。不能自行选择最常见方案再写成需求。

校对新增的“必须”“默认”“仅”“立即”和数值是否各有来源；区分建议与已批准范围。不附造虚构访谈、负责人、业务收益或客户承诺。
