# 测试文档

区分测试计划、用例设计、执行记录和测试报告。设计的预期结果不是已观察结果；“可执行”不等于“已执行”。

## 测试计划与覆盖

从指定版本的需求或契约出发，按风险选择主流程、等价类、边界、非法输入、权限、状态变化与故障恢复。只在实际有关时加入并发、兼容或迁移，不穷举无价值组合。

说明范围、排除项、环境与数据条件、重要风险和验证入口。优先级用项目定义；没有定义时给出重要性及理由，不伪造精确概率。

## 可执行用例

一条用例通常包含：稳定 ID、需求或契约链接、验证目的、前置条件、测试数据、操作步骤、可观察预期结果及优先级。已有模板优先。

- 数据应能复现边界；如最大长度来自需求，覆盖边界及其相邻值。规则未知时不能自定阈值。
- 操作明确执行者、输入与顺序；预期说明界面、响应、状态或可授权查看的数据变化。不要只写“报错”或“处理成功”。
- 一条用例围绕主要判定；等价变体可参数化。复杂步骤宜分块，避免超宽 Markdown 表格。
- 错误码、重试次数、时间上限必须有依据。判定依据未确定的用例标为待确认或阻塞，同时完成无关部分。
- 仅从现有实现提取的行为标为现状检查，不把它冒充需求正确性验证。

## 执行记录与报告

真实执行结果需要版本、环境、执行时间、实际观察、状态及必要证据或缺陷引用。只有设计任务时无需填这些栏；已有表要求时写“未执行”，不能写“通过”。

报告区分通过、失败、阻塞、未执行以及排除范围。通过率若有意义，说明分母；没有执行记录就交付报告结构或证据缺口，不能捏造统计。

发布判断要指出剩余风险和决策边界，测试完成不自动意味着批准上线或客户验收。

## 例子

已知要求：“连续五次密码错误锁定账户”，持续时间未定。可设计第 4 次、第 5 次的状态边界检查；不要给解锁用例编出 30 分钟。要求是否重置计数也未知时，将相应序列列为待确认。
