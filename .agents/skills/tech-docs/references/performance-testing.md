# 性能测试方案与报告

性能结论必须同时交代负载、环境、指标口径和观察范围。区分测试方案、实际执行、观察数据、原因假设与验收判断。编写文档不自动授权运行压测。

## 先确定要回答的问题

是验证已有性能目标、比较两个版本、定位瓶颈，还是估计容量？目标和阈值来自需求、合同或已有决定；未知时标明缺口，可以提出测量方案，不能补成已批准标准。性能优化建议与根因判断分别标明证据程度。

方案按问题选择负载类型、观测项和结束条件，不要求每个项目同时做基准、负载、压力、持续运行等所有测试。

## 让测试可以复现和解释

按对本次结论的影响记录：

- 版本与环境：构建、配置、实例数、CPU/内存、数据库、依赖服务、网络路径及关键资源限制。
- 工作负载：用户操作或接口比例、输入大小、数据量和分布、读写比例、缓存条件及认证方式。请求应代表要论证的业务场景。
- 施压方式：按到达速率发请求，还是固定并发用户、收到响应后再发？写清升压、预热、稳态时段、持续时间、重复轮次与停止条件。
- 数据采集：工具及配置、客户端/服务端测量边界、采样与聚合窗口、原始记录位置、过滤规则及排除范围。压测机是否饱和、重试与超时如何计数，都可能改变结论。

并发数是同时进行的工作数量；吞吐量是单位时间完成的工作数量。固定并发会随响应速度改变请求到达速率，不能写成固定请求率。生成器未按计划发出请求或自身成了瓶颈时，报告要说明。

## 给指标一个明确口径

- 吞吐量注明请求、事务还是业务操作，以及成功完成还是总完成；区分计划发送、实际发送和实际完成。
- 时延注明计时起止点、单位、时间窗口和纳入的请求。平均值不能替代尾部时延；P95 表示所定义样本中约 95% 的观测值不超过该值，不代表每个请求或任何时间都满足。
- 不平均多个窗口或节点的 P95 来冒充总体 P95。需要总体分位数时使用可合并的原始样本或适当的直方图；只有汇总值时明确无法恢复总体分布。
- 错误率给出分子、分母与窗口，注明超时、拒绝、业务失败、重试是否计入；HTTP 200 不自动表示业务操作成功。
- 资源利用率、排队、GC、连接池和依赖时延等按相关性选取。相关性可帮助形成瓶颈假设，不足以单独证明根因。

处理数据时保留原始材料、计算方法和单位。预热与稳态、成功与失败样本是否分开应有理由；不能静默删除不利样本。资源与版本不同的对比要说明差异，不能把所有变化归因于代码优化。

## 写结论时保留条件和限制

可裁剪结构：“问题与目标 → 本轮结论及边界 → 环境与负载 → 方法与数据 → 解释及限制 → 后续验证”。方案可省略未产生的结果；小结无需附空白报告。

结论分开表达：

1. **观察**：特定版本、环境、负载和时段中实际测得什么，并链接证据。
2. **判断**：这些结果是否支持已约定目标，缺少什么使某项无法判断。
3. **解释或建议**：瓶颈假设的依据，以及能区分解释的进一步检查；不把建议写成已验证优化。

未执行只交付方案或报告草稿。单次、短时或不代表生产的测试不能自动推出最大容量、长期稳定、生产表现或 SLA；也不能因为缺少全部生产证据，就否定本轮有用的有限结论。

示例材料：“预发环境，100 并发，稳态 10 分钟；成功请求 P95 为 180 ms；总完成 120000 个请求，失败 240 个；目标是在 2000 请求/秒下 P95 ≤ 200 ms，错误率 < 0.1%。”

可报告本轮完成请求率为 `120000 / 600 = 200 请求/秒`，错误率为 `240 / 120000 = 0.2%`，并注明计数与时延的样本口径不同。时延目标只在成功样本中达到数值，但未覆盖目标负载；错误率超过给定阈值。因此不能写“已满足目标负载下的性能要求”。不要由本轮推出“最大容量为 200 请求/秒”。
