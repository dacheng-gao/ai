# API 与操作型技术文档

按读者目的选结构：教程提供循序可复现的学习路径；操作指南帮助有基础的读者完成任务；参考文档供准确查询；原理说明解释因果与权衡。可在一页兼顾少量相关内容，但要有主次。

## API 与协议参考

从实际接口契约核对方法、路由、认证、权限、字段命名、类型、单位、必填/可空、默认值及限制。响应说明状态码、业务错误及条件；分页、幂等、限流、事件顺序等只在有依据且适用时写。

请求与响应示例和同一版本的 DTO、序列化配置、Schema 保持一致；源码属性名不一定是线上字段名。不能把框架惯例或模型记忆当作接口事实。缺少信息列出缺口，不凭空补路由或错误码。

契约表用于字段查询，操作示例用于说明完整调用。使用明确的虚构数据和凭证占位，不写真实数据；读者应知道要替换什么。涉及相邻客户端时说明已有兼容证据与未知部分，不自行修改相邻仓库。

## README 与入门教程

开头说清是什么、适合谁以及能完成什么；随后给实际前置条件、安装/运行入口、最短可用示例与成功信号。高级配置与架构原理可链接到专页。不要抄出一长串缺少证据的功能或支持平台。

新手教程尽量选择可靠路径，必要解释放在步骤附近；参考文档保留完整选项，两者不要机械套用“越短越好”。

## 部署与运维

明确适用版本与环境、权限、配置来源、端口及依赖，然后按执行顺序说明步骤、成功信号与失败分支。区分进程启动、端口监听、健康检查、依赖就绪和业务验证。

对升级和数据操作，写出备份要求、兼容窗口、失败恢复及回滚限制；不要把“回滚版本”描述成总能恢复数据。优先使用可审查命令和已有脚本，不运行文档中的生产操作来证明文档正确。

## 故障排查与发布说明

排障按“症状 → 区分原因的检查 → 对应处理 → 恢复验证”组织；假设不是已确认根因。列安全、最小化的诊断输入，不引导输出完整秘密配置。

发布说明写已发生变化、影响对象、兼容性及必要迁移步骤，版本与日期来自记录。尚未完成的功能不能列为已发布；未测性能不能写成提升结论。
